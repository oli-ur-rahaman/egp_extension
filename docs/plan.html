In scope

  • Mirror every page filter into the extension UI, each with an All checkbox
  • Handle cascading dropdowns — Ministry → Agency → PE
  • Exhaustive All iteration, expanded lazily as a tree walk
  • Pagination across result pages
  • Detail-page harvesting in a managed background tab
  • Crash-safe progress — resume after a browser restart
  • Adaptive pacing + graded recovery from throttles and logouts
  • Single-sheet flat Excel export with full filter provenance
  • Hidden Developer mode behind a secret code
  • Full run logs and audit trail

Out of scope

  • Chrome Web Store publication or auto-update infrastructure
  • Storing, typing or automating login credentials — ever
  • Downloading tender attachments and PDFs v2 candidate
  • CAPTCHA solving, WAF evasion, authentication bypass
  • IP rotation as a default operating mode
  • Any server-side component — everything runs in your browser

Definition of done · v1.0.0

  • All five flows complete a full All-iterated sprint on live eGP unattended, apart from re-login
  • A killed browser resumes within one combination — zero lost, zero duplicate rows
  • Row counts reconcile against the portal's own reported totals
  • Every selector lives in the Site Profile; none hard-coded in logic
  • Preflight catches a deliberately broken selector before a run starts
  • Secret code unlocks Dev mode; drift report exports and is machine-readable

C

Discovery — how I learn the pages

I cannot design against a site I have not seen. Seven short sessions at the browser together, each ending in a written artifact so nothing lives only in conversation.

The mechanism · CDP attach

You launch Chrome with a debug port open. I attach over the DevTools Protocol and read structure while you do all navigation, login and clicking.

separate profile — your normal Chrome untouched password fields redacted in every recon script close the window and the link is severed

Sessions

  • R0  Link-up — launch, verify attach
  • R1  Orientation — portal shell, session cookie, logout and error signatures
  • R2  Flow 1 · Procurement Transaction Report
  • R3  Flow 2 · Tender Info
  • R4  Flow 3 · APP Info + detail-tab behaviour
  • R5  Flow 4 · Contract Info
  • R6  Flow 5 · Experience Info

The per-flow checklist I will walk you through

A · Identity  ·  B · Filters

  • Exact URL — reachable directly, or only via navigation?
  • Does a hard refresh hold, or bounce to login?
  • Every filter: label, type, name/id
  • Which filters are dependent — and what fires when a parent changes
  • Which are mandatory before Search runs
  • Date formats and any max span the server enforces
  • Placeholder options to skip (--Select--, All)

C · Search & results

  • XHR or full postback? — the single biggest determinant of speed and block risk
  • Exact column headers, meanings and types
  • Does the page report a total? This is our correctness oracle
  • Pagination model; can page size be raised 20 → 100?
  • What zero results looks like — must be distinguishable from failure

D · Detail  ·  E · Failure  ·  F · Network

  • How the detail opens — link, window.open, JS handler
  • Is the detail URL deterministic? If so we skip clicking entirely
  • Does closing the tab disturb the parent's pagination?
  • Let the session expire on purpose — capture the logged-out signature
  • Record normal response timings to calibrate the slowdown detector
  • Capture the search request shape — JSON means a fast path

You do not need to prepare anything. I give one instruction at a time — "click X", "now change the Ministry dropdown", "let this sit for twenty minutes" — and explain what I am looking for each time.

Each session returns a recon note, a machine-readable Site Profile fragment, and HTML fixtures — saved page snapshots that become our offline test suite and our drift baseline. That is why later testing never has to hammer the live portal.

D

Architecture

Three layers with one rule between them: the service worker owns all state, the panel is a pure view, and the content scripts are dumb hands driven entirely by the Site Profile.

The keystone · Site Profile

Every URL, selector, column map and page rule lives in one versioned JSON file. No selector appears anywhere else in the codebase.

  • Shipped — what we captured and committed
  • Override — Dev-mode repairs, never touching the shipped file
  • Session — ephemeral, one run only

Extraction · hybrid

  • Fast path — if recon finds the search is an XHR returning structured data, replay it directly. Fewer page loads, far lower block risk.
  • UI path — otherwise, real clicks on real controls, parse the DOM.
  • Both sit behind one interface. A broken fast path falls back automatically and logs the downgrade.

Stack

  • MV3 + Side Panel API
  • Vanilla JS + Web Components — no framework to go stale
  • IndexedDB — chrome.storage is too small and too slow for thousands of rows
  • SheetJS, vendored — CSP forbids CDN loading
  • Vitest + Playwright against a local mock

Principles

  • One surface — no popup, no options page
  • Always answers three questions: what is it doing, how far along, what do I do next
  • Quiet by default — grey is rest, colour means something
  • Honest progress — ≈ when the total is an estimate, never a fake percentage
  • No dead ends — every error names the problem and offers the next action

Interaction rules

  • All disables its select and shows the option count — you always know the size of what you asked for
  • All on a parent implies iterating its children; the UI says so rather than leaving you to infer it
  • Start stays disabled until the page matches and the plan is computable, with the reason shown inline
  • Stop asks once, then exports what was collected — never discards it

Dev mode entry

Nothing hints it exists. Click the version number in the footer seven times to reveal a single unlabelled input.

A wrong code does nothing at all — no error, no shake, no hint that a code even exists.

I

Guardian — surviving the site changing

eGP will change its HTML. Four layers of defence, then a gated repair path where you choose which route to take.

Layer 1

Resilient selectors

Ordered fallbacks and a semantic strategy — find by label text, never by a generated ID like ctl00_…_ddl3 alone.

Layer 2

Preflight check

Every selector asserted before each run. A failure blocks the run and names the culprit. You never get corrupt data — you get a stop.

Layer 3

Runtime assertions

Column count, header text and value types checked per page. A silently shifted column is caught, not exported.

Layer 4

Structural fingerprint

A normalised DOM skeleton hash per page, so we can tell a cosmetic change from a structural one.

Versioning & audit

  • Profile is semver'd — patch = selector fix, minor = new field, major = restructure
  • CHANGELOG-PROFILE.md records every change, its cause, and the drift report behind it
  • Extracted data carries its profileVersion — you can always tell which rules produced a file
  • Each run stores a manifest: versions, timestamp, filter config, counts, warnings

Standing maintenance rhythm

  • Every run — preflight, automatic and invisible unless it fails
  • Monthly — you open Dev, run a full health scan. Two minutes. Catches drift before it interrupts real work
  • On any anomaly — odd counts, missing columns, unexplained stops: export the drift report, send it to me
  • After each repair — fixtures refreshed, goldens updated, fingerprint baseline re-based

On IP rotation — my recommendation

You raised it; I'd advise against it, and it probably wouldn't fix your problem anyway.

  • Throttling on an authenticated portal is almost certainly per account, not per IP. Rotating buys nothing.
  • A mid-session IP change is the textbook session-hijack signature — the likely result is being logged out more, not less.
  • It exposes your real eGP identity to a deliberate-circumvention finding. The technical risk is small; the account risk is not.
  • Your symptom — "stops and does not start over" — is a resume defect. Checkpointing plus the recovery ladder addresses it directly.

Ship without proxying, instrument thoroughly. If Phase 7 produces hard evidence of IP-scoped blocking, we reopen it with data. The architecture leaves a clean extension point; the manifest deliberately does not request the permission.

Posture — legal, security, data integrity

  • Data is accessed through your own account, with rights you already hold. The extension automates your clicks; it obtains nothing you could not obtain manually.
  • No authentication bypass, no CAPTCHA solving, no WAF evasion. If the portal genuinely blocks us, we slow down.
  • Minimum permissions, host-scoped to *://*.eprocure.gov.bd/*. No analytics, no telemetry, no outbound calls except Path B when you trigger it.
  • Every row carries run_id, combination_id, its filter values, source_url and extracted_at — any row traces back to the page it came from.
  • Dates parse to real dates, IDs stay text so leading zeros survive, and a missing value is empty — never zero, never "N/A".
